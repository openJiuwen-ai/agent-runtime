# 全链路安全

## 功能说明

JiuwenSwarm 企业版的内部链路认证通过双向 TLS（mTLS）和证书绑定保护受管组件之间的 HTTP/SSE 流量，校验服务身份以及该身份对当前接口和绑定的访问权限。

启用后，请求先经过 TLS 握手。客户端校验服务端证书链、有效期和访问地址是否匹配证书的 SAN（主题备用名称），并核对目标证书指纹。服务端要求客户端出示证书，从实际 TLS 连接中读取对端证书，按接口校验证书指纹对应的服务角色，再校验请求的绑定 ID 和绑定代次。这样，即使两个服务使用同一 CA 签发的证书，也只能调用其角色和绑定允许的接口。

### 保护范围

| 调用链路 | 调用方证书角色 | 受保护的操作 |
| --- | --- | --- |
| Manager → Gateway | `manager` | 下发网关配置。 |
| Manager → Runtime | `manager` | 同步运行时配置。 |
| Gateway → Runtime | `gateway` | 会话路由、保活、清理、配置刷新和会话改绑。 |
| Gateway → AgentServer | `gateway` | AgentServer 的内部 HTTP 业务调用及 SSE 流式响应。 |

Runtime 按需创建 AgentServer 时，将 `agentserver` 角色的证书材料挂载到主容器，并返回与证书 SAN 匹配的 HTTPS Pod DNS 地址。一个绑定内的 AgentServer 副本共享该角色证书，同一绑定中的 Gateway、Runtime、AgentServer 和 Manager 分别使用各自角色的私钥。AgentServer 在 SSE 流式响应期间继续检查绑定，在读到绑定失效或证书指纹不再受信时终止流。

浏览器入口的 HTTPS、员工身份认证和用户访问 Agent 的权限由各自的入口或授权机制管理，分别参见[集群部署指南](../快速开始/集群部署指南.md)、[企业认证服务接入](../开发者指南/接口文档/企业认证服务接入.md)和[集群准入](统一管理平台/集群管理/集群准入.md)。

## 使用流程概览

1. 准备同一交付版本的部署工具和组件镜像，确认 Gateway、Runtime 的数据库及服务地址。
2. 在部署工具目录的 `.env.custom` 中设置 `JIUWENSWARM_LINK_MTLS_MODE=enforce`，并按部署形态更新相关组件。
3. 部署工具签发或恢复角色证书和绑定信息，并为相应组件挂载材料。Manager 为每个受管实例选用对应的绑定。
4. 检查部署日志和内部 HTTPS 健康接口，再通过一次实际对话验证会话路由、AgentServer 调用和流式回复。

## 部署配置

### 准备工作

- 使用提供内部链路 mTLS 的配套部署包和组件镜像。部署工具需能准备并挂载证书，Gateway、Runtime、AgentServer 需支持相应的 TLS 监听和角色校验，Manager 需支持按实例绑定下发配置。部署节点需要能运行 Docker，并能访问数据库和目标 Kubernetes 命名空间。
- 使用部署工具支持的 MySQL 兼容数据库或 PostgreSQL。Gateway 和 Runtime 使用独立数据库，PostgreSQL 也可以使用同一数据库下不同的 schema。部署工具需要连接可写数据库端点来保存及恢复证书材料。
- 部署前确定 Gateway、Runtime 的内部服务名称、端口和集群 DNS 域。域名会进入证书校验，修改服务地址时需同步检查证书和绑定记录。

### 设置认证模式

在 `.env.custom` 中设置 `JIUWENSWARM_LINK_MTLS_MODE`。设置在部署到相应进程后生效。

| 取值 | 行为 |
| --- | --- |
| `off`（默认） | 沿用既有传输方式，跳过证书生成和持久化。 |
| `observe` | 预检本地已有证书材料，继续使用既有传输方式。 |
| `enforce` | 受管内部链路使用 HTTPS，最低 TLS 版本为 1.2，强制执行双向证书、角色及绑定校验。认证失败时终止请求。 |

```ini
JIUWENSWARM_LINK_MTLS_MODE=enforce
```

部署工具会为各角色准备证书、私钥、CA 公共证书和内部 `profile.json`，并生成 mTLS 部署 ID、绑定 ID 和绑定代次。首次部署和普通升级均由工具处理这些参数。

### 部署或更新相关组件

以下以支持内部链路 mTLS 的 Kubernetes 部署包为例。完成基础服务部署后，在部署包目录更新产品组件和管理套件，将 `example-app` 替换为实际命名空间。基础服务和部署顺序见[集群部署指南](../快速开始/集群部署指南.md#3-部署产品服务)。

```bash
./deploy.sh up -n example-app
./deploy.sh up manager -n example-app
```

从 `off` 切换到 `enforce` 时，在维护窗口统一更新相关组件，并安排尚未挂载证书的 AgentServer 有序退出，由 Runtime 按需重新创建。

### Manager 如何绑定受管实例

Manager 使用业务实例 ID `jiuwenclaw_id` 查找 `instance_link_binding`，并从同一条记录选取 Gateway 和 Runtime 的目标地址、信任包及目标证书指纹。请求的 `X-Jiuwenswarm-Mtls-Binding-Id` 和 `X-Jiuwenswarm-Mtls-Binding-Epoch` 分别来自 `mtls_binding_id` 和 `mtls_binding_epoch`。

- **同一部署工具创建的实例**：当实例的 Gateway 和 Runtime 配置地址均与部署记录精确匹配时，Manager 在首次配置同步时自动登记绑定。
- **独立部署的受管实例**：先让 Manager 能通过其信任的证书链访问目标，再为已注册的实例以管理员身份调用 `PUT /api/v1/instances/{jiuwenclaw_id}/link-binding`。登记 `mtls_gateway_endpoint`、`mtls_runtime_endpoint`、各角色证书指纹、绑定 ID、代次和信任包引用 `trust_bundle_ref`，然后同步配置。两个地址分别按 `host:port` 精确匹配实例的 `gateway_host` 和 `runtime_host`，地址中不得包含凭据、路径、查询参数或片段。

请求字段及格式见 [Manager 实例链路绑定接口模型](https://gitcode.com/openJiuwen/agent-runtime/blob/develop/applications/manager/manager_server/src/manager_server/schemas/link_binding_schemas.py)。

## 验证生效

1. 检查部署日志中的 `mTLS binding ready`。首次签发显示 `reused=false`，使用原有证书材料重新部署显示 `reused=true`。复用时指纹、绑定代次和到期时间保持一致。
2. 在 Gateway 容器内使用该组件的角色身份访问 Gateway 和 Runtime 的内部健康接口。示例使用默认 Deployment 和容器名称，自定义部署时替换为实际名称。预期输出 `gateway 200` 和 `runtime 200`。

   ```bash
   kubectl -n example-app exec deployment/jiuwenswarm-gateway -c gateway -- python -c '
   import asyncio
   import httpx
   from openjiuwen_runtime.foundation.security.link_profile import load_service_identity

   async def main():
       identity = load_service_identity("gateway")
       for role, path in (("gateway", "/api/v1/ready"), ("runtime", "/healthz")):
           url = identity.endpoint(f"link://{role}{path}", role=role)
           async with httpx.AsyncClient(
               trust_env=False, timeout=5, **identity.client_kwargs(role=role)
           ) as client:
               response = await client.get(url)
               response.raise_for_status()
               print(role, response.status_code)

   asyncio.run(main())
   '
   ```

3. 使用已授权用户从用户面发起新对话，确认 Runtime 完成路由、AgentServer 正常执行并返回流式回复。检查新建的 AgentServer 是否挂载对应的 Secret，以及路由是否使用 HTTPS Pod DNS 地址。健康接口用于验证 TLS 和证书身份，业务接口还会检查调用角色和绑定头。会话准备和授权步骤见[快速上手](../快速开始/快速上手.md)。

## 证书保管与运维

| 保存位置 | 保存内容 |
| --- | --- |
| Gateway 数据库的 `link_binding_state` 表 | 绑定记录及可恢复的完整角色材料，包括角色私钥。 |
| Runtime 数据库的 `link_binding_state` 表 | 公开绑定状态、证书指纹和 AgentServer Secret 引用。 |
| Kubernetes Secret | `jiuwenswarm-link-gateway`、`jiuwenswarm-link-runtime`、`jiuwenswarm-link-agentserver`、`jiuwenswarm-link-manager` 分别保存对应角色的运行材料。 |
| Manager 数据库的 `instance_link_binding` 表 | 内置 Manager 的业务实例与 mTLS 绑定、目标证书指纹及信任包引用的映射。 |

首次签发的证书有效期为十个公历年。使用相同数据库和受管地址重新部署时，工具复用已有证书、私钥和绑定信息。数据库材料完整且 Secret 缺失时，工具可恢复原材料。若数据库与 Secret 冲突、证书到期或服务地址已变化，部署会停止，需要按实际原因处理。

证书私钥保存于 Gateway 数据库和对应角色的 Secret。应限制对数据库敏感字段、备份和 Secret 的访问权限，排查时只记录状态码、指纹或到期时间等公开信息。证书续期采用维护窗口内的受控换证流程，初次签发使用的 CA 私钥在签发后即丢弃。遇到证书临期、私钥泄漏或绑定变更时，需要协调重新签发、信任更新和相关进程重启。关闭已启用的认证时，也需一并更新相关组件、已创建的 AgentServer 和调用地址。

## 常见问题

| 现象 | 检查项 |
| --- | --- |
| 没有出现 `mTLS binding ready` | 确认实际执行 `up` 的部署工具版本、目标命名空间和 `.env.custom` 中的 `enforce`。检查数据库可写性、Gateway 与 Runtime 的库或 schema 是否分离。 |
| TLS 握手失败或 HTTPS 请求中断 | 检查客户端证书、CA 信任、证书有效期和访问地址的 SAN。客户端缺少证书时，连接可能在 TLS 层被拒绝，收不到 HTTP 状态码。 |
| 接口返回 `403` 和 `LINK_BINDING_MISMATCH` | 对照接口允许的服务角色，检查对端证书指纹是否属于该角色，以及绑定 ID、代次和目标地址是否来自同一条绑定。 |
| 切换到 `enforce` 后，健康检查通过但旧会话对话失败 | 检查会话是否仍指向切换前的 AgentServer，以及目标是否已使用带证书的 HTTPS Pod DNS 地址。按维护计划更新旧实例，再验证会话。 |
| 更新后提示数据库和 Secret 不一致 | 检查数据库及其备份的来源、当前服务地址和绑定材料。保留现有材料用于核对，按同一套有效绑定恢复。 |
