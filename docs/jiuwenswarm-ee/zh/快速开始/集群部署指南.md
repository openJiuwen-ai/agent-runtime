# 集群部署指南

本文介绍在 Kubernetes / OpenShift 集群上部署、卸载 JiuwenSwarm 企业版产品组件与基础服务的完整流程。

## 1. 部署基础服务

基础服务指 NFS 存储、数据库与对象存储（OBS），均支持两种来源，可按环境选择：

- **内置部署（开发环境可用）**：由部署工具拉起并托管（`./deploy.sh up <组件>`），地址 / 凭证自动派生注入，开箱即用；
- **外部独立部署（生产环境推荐）**：在 `.env.custom` 中填写已有服务的连接地址与凭证，产品组件直连外部服务，工具不再部署对应内置组件（部署预检自动豁免）。

内置基础服务均为 StatefulSet 单实例形态，实例定位规则：本次部署目标命名空间内已有则复用，其次复用 `default` 命名空间中的共享实例（k8s 形态多套环境共用一套基础服务的推荐做法），均未命中才新建。`secret`（全部组件的密码注入源）随首个 `up` 自动创建，无需单独部署。

### 1.1 部署 NFS 服务（仅 k8s 形态）

**作用与形态限制**：NFS 直连挂载仅 `CLUSTER_TYPE=k8s` 生效——k8s 形态不渲染 PVC（共享工作区 PVC 清单按形态剔除），mariadb / mysql / postgresql / minio / agentserver 的数据卷与共享工作区全部直连挂载 NFS；**OpenShift 形态不使用 NFS**，存储走 PVC + StorageClass（`DATA_STORAGE_CLASS` / `WORKSPACE_STORAGE_CLASS`），无需配置本节变量。

NFS 同样分内置与外挂两种来源，由 `NFS_SERVER_ADDR` 是否为空决定。

#### 1.1.1 使用集群预置 NFS server（开发环境可用）

`NFS_SERVER_ADDR` 留空（默认）时，使用集群中预置的 NFS server Pod（`default` 命名空间、label `app=nfs-server`，Pod 内导出根 `/exports` 为节点 hostPath）。

前置条件：集群中已运行该 NFS server Pod。工具部署时自动解析其所在节点 IP 作为挂载地址，并自动创建数据目录 `<NFS_SHARE_PATH>/<NAMESPACE>/<组件>`（Pod 内 `mkdir` + `chmod 777`，随机 uid 可写）；未找到该 Pod 时部署终止并提示。

#### 1.1.2 外部独立部署 NFS 服务（生产环境推荐）

生产环境下，推荐用户自行搭建高可用的外部 NFS 服务，搭建完成后需在 `.env.custom` 中填写如下参数，完成外部 NFS 服务的对接工作：

```bash
# 外部 NFS 服务的连接地址（主机名或 IP），填写即启用外挂模式
# 留空时使用集群预置 NFS server（见 1.1.1）
NFS_SERVER_ADDR=192.168.1.100

# NFS v4 导出根（伪根）下的共享根目录，须为绝对路径
# 如服务器将 /data/nfs 配为导出根（fsid=0），此处填 /，数据实际落在服务器 /data/nfs 下
NFS_SHARE_PATH=/
```

**前置约束**：数据目录 `<NFS_SHARE_PATH>/<NAMESPACE>/<组件>` 须在 NFS 服务器上**预先创建**（内置模式由工具自动创建，外部模式不代建）。

限制说明：

- 地址须为主机名或 IP、共享路径须为绝对路径，非法值部署报错；
- `--render-only` 模式下不做 NFS 直连改写（内置模式需连接集群解析 NFS 地址），完整部署请走 `up`；卸载（`down`）按资源名删除，不受 NFS 地址解析影响。

### 1.2 部署数据库服务

支持 MariaDB / MySQL / PostgreSQL 三种数据库，由 `DB_TYPE` 指定（非法值部署报错），同时决定内置部署的数据库类型与各组件连接驱动。内置 / 外挂的唯一判据为 `DB_HOST` 是否为空。各业务组件启动时由框架自动建库建表（`CREATE DATABASE IF NOT EXISTS`），无需手工建库。

#### 1.2.1 工具内置部署（开发环境可用）

```bash
./deploy.sh up mariadb      # 部署内置数据库（按 DB_TYPE 三选一: mariadb / mysql / postgresql）
```

连接信息自动派生，无需手工配置：

| 项 | 派生值 |
|---|---|
| 地址 | `mariadb / mysql / postgresql-headless.<命名空间>` |
| 端口 | mariadb / mysql=3306，postgresql=5432 |
| 用户 | mariadb / mysql=root，postgresql=postgres |
| 密码 | 取 `DB_TYPE` 对应的 `MARIADB_ROOT_PASSWORD` / `MYSQL_ROOT_PASSWORD` / `POSTGRES_PASSWORD` |

**注意**：内置数据库为单实例 standalone 形态，如需高可用数据库服务，请采用外部独立部署方式；数据库 root 密码仅**首次初始化**生效，已初始化实例改密须同步在库内 `ALTER USER`。

#### 1.2.2 外部独立部署（生产环境推荐）

生产环境下，推荐用户自行搭建高可用的外部数据库服务，搭建完成后需在 `.env.custom` 中填写如下参数，完成外部数据库服务的对接工作：

```bash
# 数据库类型（同时决定连接驱动）
DB_TYPE=mariadb

# 外部数据库服务的连接地址，填写即启用外挂模式
DB_HOST=192.168.1.101

# 外部数据库服务的连接端口，留空按 DB_TYPE 取默认（mariadb / mysql=3306，postgresql=5432）
DB_PORT=3306

# 外部数据库服务的用户名与密码，账号权限区分规则：
# 1. 分库独立账号配置：定义 <模块>_DB_USER / <模块>_DB_PASSWORD（模块集 GATEWAY / WEB / IDENTITY / MANAGER / RUNTIME）
# 2. 全局统一账号配置：仅配置 DB_USER / DB_PASSWORD
# 优先级规则：分库专属账号变量优先级 > 全局统一账号变量；两类同时配置时以分库专属为准
# 说明：AgentServer 连接 Gateway 库，无独立账号变量，凭证跟随 GATEWAY
DB_USER=jswarm
DB_PASSWORD=<统一密码>
```

**密码优先级**：`DB_PASSWORD` > `DB_TYPE` 对应的 ROOT 密码变量，两者均未设置时部署报错（外部数据库必须提供密码）。

#### 1.2.3 多实例数据库隔离

多实例（多命名空间）部署场景下，各模块默认按命名空间自动隔离，无需手动配置：

- **MariaDB / MySQL**：每模块使用形如 `<模块>_<命名空间>` 的独立数据库（如命名空间 `test` 的 Gateway 库为 `gateway_test`）；
- **PostgreSQL**：每模块使用独立数据库 `<模块>`，并以命名空间命名的独立 schema 隔离（如 schema `test`）。

库名 / schema 可用 `GATEWAY_DB_NAME` / `WEB_DB_NAME` / `RUNTIME_DB_NAME` / `IDENTITY_DB_NAME` / `MANAGER_DB_NAME`（PostgreSQL 为 `*_PG_SCHEMA`）显式指定——**请务必保证同一套部署中每个实例的各模块库名（或 schema 名）互不相同**，否则不同实例会读写同一数据库，导致数据串台。

### 1.3 部署对象存储（OBS）服务

系统支持两种对象存储接入方案：部署工具内置部署的 MinIO 实例，或对接外部独立对象存储服务（S3 / MinIO 兼容协议），按需选择。内置 / 外挂的唯一判据为 `OBS_URL` 是否为空。

#### 1.3.1 工具内置部署 MinIO 服务（开发环境可用）

```bash
./deploy.sh up minio        # 部署 MinIO 存储模块
```

连接信息自动派生，无需手工配置：

| 项 | 派生值 |
|---|---|
| 地址 | `minio-headless.<命名空间>:9000`（S3 API 9000，Console 9001） |
| 桶名 | 默认 `jiuwenswarm`（`OBS_BUCKET` 无需配置） |
| AccessKey / SecretKey | 自动取 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`（已填的外部 AK/SK 会被忽略，避免凭证错配） |
| HTTPS / 区域 | 固定关闭 / 默认 `default` |

内置 MinIO 仅提供集群内访问。

**注意**：内置 MinIO 为单实例 standalone 形态，如需高可用对象存储服务，请采用外部独立部署方式。

#### 1.3.2 使用外部 OBS 服务（生产环境推荐）

生产环境下，推荐用户自行搭建或购买高可用的外部 OBS 服务，搭建完成后需在 `.env.custom` 中填写如下参数，完成外部 OBS 服务的对接工作：

```bash
# 外部对象存储(S3/MinIO兼容)接入地址，填写即启用外挂模式
OBS_URL=obs.cn-north-4.myhuaweicloud.com

# 业务存储桶名称（外部 OBS 必填）
OBS_BUCKET=jswarm-files

# 对象存储访问的 AccessKey / SecretKey（外部 OBS 必填，填写云厂商/兼容 S3 服务的 AK/SK）
OBS_ACCESS_KEY=<AK>
OBS_SECRET_KEY=<SK>

# 客户端连接是否启用 HTTPS
# 生产环境请勿关闭 HTTPS，否则 AK/SK 与业务文件将明文传输；
# 留空默认 false，请以服务端实际 SSL 开关为准
OBS_SECURE=true

# 对象存储区域标识，按需填写
OBS_REGION=

# 对象存储公网预览访问域名
# 仅文件需要浏览器公网直读场景配置，内网环境可不填
OBS_PUBLIC_BASE_URL=
```

**必填校验**：启用外部 OBS 后，`OBS_BUCKET`、`OBS_ACCESS_KEY`、`OBS_SECRET_KEY` 任一缺失部署即报错。

## 2. 配置 .env.custom

部署工具的全部行为由部署目录下的 `.env.custom` 控制。`.env.custom` 随部署工具安装包一并发布（获取方式见[《快速上手》"下载部署工具"](快速上手.md#下载部署工具)），**大部分变量已预置好，可直接使用**；各变量的含义与取值说明详见部署工具目录下的 `.env.example`，部署工具的完整使用说明（命令详解、组件清单、程序化调用等）见部署工具目录下的 `README.md`，基础服务（NFS / 数据库 / OBS）的内置 / 外挂配置见 [1.1](#11-部署-nfs-服务仅-k8s-形态)、[1.2](#12-部署数据库服务)、[1.3](#13-部署对象存储obs服务) 节。

部署产品服务前，请务必按集群形态确认以下配置：

```bash
# openshift 集群：请务必设置这两个值——openshift 形态没有 NFS 直连挂载，
# 数据库 / 对象存储 / AgentServer 的数据卷与共享工作区全部走 PVC 动态供给
DATA_STORAGE_CLASS=         # 数据库 / MinIO / AgentServer 数据卷的块存储 StorageClass
WORKSPACE_STORAGE_CLASS=    # 共享工作区 PVC 的 StorageClass（需支持 ReadWriteMany）

# k8s 集群：请务必设置这个值（默认值是 openshift，openshift 集群不需要专门配置）
CLUSTER_TYPE=k8s
```

## 3. 部署产品服务

```bash
./deploy.sh up            # 产品组件（按 AGENT_RUNTIME_DEPLOY_MODE 派生）:
                          #   off:     secret → redis → agentserver → gateway → web
                          #   routing: secret → redis → runtime → agentserver → gateway → web
                          #   full:    secret → redis → runtime → gateway → web
                          #          （AgentServer 由 runtime 按需创建，自动注入 Pod 操作 RBAC）
./deploy.sh up manager    # 管理套件: identity → manager-server → manager-web
```



行为说明：

- **namespace**：全部组件由 `NAMESPACE` 统一控制，也可 `./deploy.sh up -n <ns>` 临时指定；数据库建库的库名后缀同样取自 `NAMESPACE`（更换 namespace 即使用对应后缀的独立库）；
- **顺序即依赖**：agentserver 先于 gateway、runtime 先于 agentserver（注册接收方），脚本已保证；共享依赖 secret / redis 缺失时随 `up` 自动拉起，已存在则复用；基础服务（mariadb / minio）缺失时终止并提示，`./deploy.sh up mariadb minio` 拉起即可（已配置外挂数据库 / OBS 时不再要求部署对应内置组件）；
- **幂等**：可重复执行，已存在资源自动跳过；副本数被人为调整过会自动恢复；
- **就绪等待**：每个组件部署后轮询等待 Pod 就绪（默认预算 300s）。首次拉取镜像较慢时调大预算：`WAIT_TIMEOUT_SECS=600 ./deploy.sh up`


## 4. 卸载产品服务

```bash
./deploy.sh down manager   # 卸载管理套件（倒序: manager-web → manager-server → identity）
./deploy.sh down           # 卸载产品组件（倒序: web → gateway → agentserver → redis → secret）
```

- **数据不可恢复**：PVC / 数据目录随组件一并删除，需要保留请先导出；
- **共享依赖自动保留**：secret / redis 卸载时若仍被存活组件依赖会跳过删除（如先 `down` 产品组时管理套件还在），全部卸载后再补一次 `down` 即可清干净；
- 每个组件删除后脚本会等其 Pod 删净再继续。

## 5. 只渲染清单（不连集群）

渲染产物输出到 conf/，染全套 K8s/Openshift  资源清单，仅生成 YAML 不直接操作集群，适配本地运维机与 K8s/Openshift 集群分离场景，无需手动编写 / 修改资源模板。

```bash
./deploy.sh up --render-only -n <命名空间> 
./deploy.sh up manager --render-only -n <命名空间> 
```

## 6. 访问服务

**OpenShift 形态**：部署工具自动为 manager-web 创建 Route，部署完成后查看实际域名（`<name>-<namespace>.<集群ingress域名>`），浏览器从任何网络直接访问，无需 port-forward：

```bash
kubectl get route -n <namespace>
```

```text
https://jiuwenswarm-manager-web-<ns>.<ingress域名>
```

**k8s 形态**：自动追加 manager-web NodePort Service：

```bash
kubectl get svc -n <namespace> jiuwenswarm-manager-web-nodeport
```

访问 `http://<节点IP>:<nodePort>`。

两种形态下，这都是唯一需要记住的入口：从管理面登录后点击进入用户面，**不要直接访问 web 组件地址**（用户面鉴权代理在 manager-web 的 nginx 上）。管理员默认账号 `admin / admin`，首次登录后请立即修改密码。
