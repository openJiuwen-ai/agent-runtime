# 集群部署指南

本文介绍在 Kubernetes / OpenShift 集群上部署、卸载 JiuwenSwarm 企业版产品组件与基础服务的完整流程。

## 1. 部署工具包介绍

JiuwenSwarm 企业版部署工具包是一组自包含的部署脚本与清单模板：将 `templates/` 下的 K8s / OpenShift 资源清单模板按 `.env.custom` 渲染为实际清单，并按依赖顺序提交到目标集群，完成产品组件与基础服务的一键部署 / 卸载，适配 OpenShift 与原生 Kubernetes 两种集群形态。

**获取方式**：从官网获取下载地址，按部署节点 CPU 架构（`uname -m` 查看）选择 amd64 / arm64 对应安装包，`wget` 下载、`unzip` 解压后进入解压目录即可使用。

**包内容一览**（解压后）：

| 条目 | 用途 |
| --- | --- |
| `deploy.sh` | 唯一入口：`up` 部署 / `down` 卸载，支持按组件、按管理套件执行 |
| `templates/` | 全部资源清单模板（`<<VAR>>` 占位符）：产品组件、管理套件、内置基础服务（mariadb / mysql / postgresql / minio / redis）、PVC 等 |
| `conf/` | 渲染产物输出目录：部署与 `--render-only` 时自动生成 |
| `.env.custom` | 用户配置文件：部署行为的唯一控制入口，大部分变量已预置可直接使用 |
| `.env.example` | 部署变量字典：各变量的含义与取值说明详见此文件 |
| 其余 `*.sh` | 内部分层实现：命令行解析、`.env.custom` 读取、变量校验与派生、清单渲染、组件映射与依赖预检、双集群形态（k8s / openshift）清单改写、REST 提交、就绪等待与卸载——日常使用无需直接调用 |

## 2. 部署基础服务（NFS 存储 / 数据库 / 对象存储）

产品组件运行所依赖的基础服务包含三类：**NFS 存储、数据库、对象存储（OBS）**，均支持两种来源，可按环境选择：

- **内置部署（开发环境可用）**：由部署工具拉起并托管（`./deploy.sh up <组件>`），地址 / 凭证自动派生注入，开箱即用；
- **外部独立部署（生产环境推荐）**：在 `.env.custom` 中填写已有服务的连接地址与凭证，产品组件直连外部服务，工具不再部署对应内置组件（部署预检自动豁免）。

内置基础服务均为 StatefulSet 单实例形态，实例定位规则：本次部署目标命名空间内已有则复用，其次复用 `default` 命名空间中的共享实例（k8s 形态多套环境共用一套基础服务的推荐做法），均未命中才新建。`secret`（全部组件的密码注入源）随首个 `up` 自动创建，无需单独部署。

### 2.1 部署存储服务（NFS / StorageClass）

两个集群形态的存储模式不同：

- **k8s 形态：挂载模式由 `MOUNT_TYPE` 决定**——`sc`（默认）为 StorageClass 动态供给模式：数据卷走 PVC（见 2.1.1 / 2.1.3）；`nfs` 为 NFS 直连模式（历史行为，显式选择）：数据卷不渲染 PVC，全部直连挂载 NFS，`NFS_SERVER_ADDR` 留空时使用内置 NFS server（见 2.1.1），填写时使用外部 NFS 服务（见 2.1.2）；
- **OpenShift 形态：StorageClass 模式**——数据卷与共享工作区全部走 PVC 动态供给：部署内置 NFS 存储供给组件 nfs-sc（见 2.1.1）时自动使用其 StorageClass；未部署 nfs-sc 且未配置 `DATA_STORAGE_CLASS` / `WORKSPACE_STORAGE_CLASS` 时走集群默认 StorageClass；生产环境也可直接指定企业已有的 StorageClass（见 2.1.3）。

#### 2.1.1 NFS 存储内置部署（开发环境可用）

一条命令 `./deploy.sh up nfs` 同时覆盖内置 NFS server 与 NFS 存储供给组件（nfs-sc）：工具会按部署平台自动调整部署目标（`--render-only` 离线渲染除外），规则如下：

| 部署平台 | 实际部署目标 | 前置配置 |
| --- | --- | --- |
| k8s 集群，部署节点为 amd64 | nfs（内置 NFS server）+ nfs-sc（存储供给组件） | 无需额外配置，开箱即用 |
| k8s 集群，部署节点为 arm64（等非 amd64） | 仅 nfs-sc | `.env.custom` 配置 `NFS_SERVER_ADDR` 指向外部 NFS server |
| OpenShift 形态 | 仅 nfs-sc | `.env.custom` 配置 `NFS_SERVER_ADDR` 指向外部 NFS server |

arm64 / OpenShift 平台未配置 `NFS_SERVER_ADDR` 时，部署预检会报错指引配置，不会盲目拉起数据源缺失的供给组件。按需配置 NFS 数据目录（`.env.custom`，示例值按实际环境修改）：

```bash
# NFS 数据目录（部署节点本地目录，仅 amd64 k8s 的内置 NFS server 使用），默认 /data/nfs
NFS_HOST_PATH=/data/nfs
```

配置完成后执行部署：

```bash
./deploy.sh up nfs    # amd64：NFS server + nfs-sc 一次拉起；arm64 / openshift：仅 nfs-sc
```

部署完成后，nfs-sc 自动生成对应 StorageClass（默认名 `jiuwenswarm-storage`，可用 `NFS_SC_NAME` 调整）。`DATA_STORAGE_CLASS` / `WORKSPACE_STORAGE_CLASS` 留空时（部署 nfs-sc 或集群中已存在供给组件）自动填充为该 StorageClass 名，业务 PVC 即可动态申领独立 NFS 子目录。

说明：

- NFS server 以 hostNetwork 绑定节点 2049 端口、固定调度到运行部署工具的节点，**全集群仅能存活一套**——请勿在多个命名空间重复部署，推荐 `-n default` 部署共享实例供多套环境共用；
- 数据目录 `<NFS_SHARE_PATH>/<NAMESPACE>/<组件>` 在组件部署时自动创建（默认共享根 `/`）；
- 卸载 `./deploy.sh down nfs` 与 `up nfs` 规则对称（amd64 k8s 卸载 nfs + nfs-sc；arm64 k8s / OpenShift 卸载 nfs-sc），节点上的导出根数据目录保留；
- StorageClass 与供给组件为全集群共享资源，只需也只能部署一次，请勿在多个命名空间重复部署；
- 依赖 NFS 的组件（mariadb / mysql / postgresql / minio / agentserver）部署前 NFS 须已就绪，缺失时部署预检会提示先执行 `up nfs`。

#### 2.1.2 NFS 外部部署（生产环境推荐）

生产环境推荐自行搭建高可用的外部 NFS 服务。外部 NFS 在两类场景下作为数据源使用：

- **k8s 形态 + `MOUNT_TYPE=nfs` 直连模式**：数据卷直连挂载外部 NFS，替代内置 NFS server；
- **arm64 k8s / OpenShift 形态的 nfs-sc**：内置 NFS server 在这两类平台不可用（见 2.1.1），nfs-sc 须以外部 NFS 为数据源。

搭建完成后，在 `.env.custom` 中填写如下参数完成对接：

```bash
# 外部 NFS 服务的连接地址（主机名或 IP），填写即启用外挂模式
# k8s 形态 MOUNT_TYPE=nfs 时留空使用内置 NFS server（见 2.1.1）；
# arm64 k8s / openshift 形态部署 nfs-sc 时必填
NFS_SERVER_ADDR=192.168.1.100

# NFS v4 导出根（伪根）下的共享根目录，须为绝对路径
# 如服务器将 /data/nfs 配为导出根（fsid=0），此处填 /，数据实际落在服务器 /data/nfs 下
NFS_SHARE_PATH=/
```

**前置约束**（仅 `MOUNT_TYPE=nfs` 直连模式适用）：数据目录 `<NFS_SHARE_PATH>/<NAMESPACE>/<组件>` 须在 NFS 服务器上**预先创建**，组件固定为五类：**mariadb / mysql / postgresql / minio / agentserver**（redis 为纯缓存不落盘，无需目录；数据库三选一，按 `DB_TYPE` 实际使用的建对应目录即可）。其中 `<NAMESPACE>` 按组件实际部署位置取值：基础服务（数据库 / minio）绝大多数复用 `default` 命名空间中的共享实例，**按基础服务实际所在命名空间建目录**；agentserver 随业务部署，**按业务命名空间建目录**。用 `mkdir -p` 创建并 `chmod 777` 授权，保证随机 uid 客户端读写；内置模式由工具自动创建，外部模式不代建。`MOUNT_TYPE=sc`（PVC 动态供给）无需手工创建——nfs-sc 供给器自动建子目录，仅要求导出根可写。

```bash
# 示例 1：基础服务部署在 default 命名空间共享实例（绝大多数场景）、DB_TYPE=mariadb、共享根 /data/nfs（路径按实际环境修改）
mkdir -p /data/nfs/default/mariadb /data/nfs/default/minio
chmod -R 777 /data/nfs/default

# 示例 2：AgentServer 部署在业务命名空间 jiuwenswarm
mkdir -p /data/nfs/jiuwenswarm/agentserver
chmod -R 777 /data/nfs/jiuwenswarm

# 基础服务部署在业务命名空间时（少数场景），示例 1 的 default 替换为对应业务命名空间即可
```

#### 2.1.3 指定企业已有 StorageClass（生产环境推荐）

生产环境的集群通常已有企业统一管理的 StorageClass，无需部署 nfs-sc 供给组件——直接在 `.env.custom` 中指定即可（k8s 形态默认即为 `sc` 模式）：

```bash
DATA_STORAGE_CLASS=         # 数据库 / MinIO / AgentServer 数据卷的块存储 StorageClass
WORKSPACE_STORAGE_CLASS=    # 共享工作区 PVC 的 StorageClass（需支持 ReadWriteMany）
```

### 2.2 部署数据库服务

支持 MariaDB / MySQL / PostgreSQL 三种数据库，由 `DB_TYPE` 指定（非法值部署报错），同时决定内置部署的数据库类型与各组件连接驱动。内置 / 外挂的唯一判据为 `DB_HOST` 是否为空。各业务组件启动时由框架自动建库建表（`CREATE DATABASE IF NOT EXISTS`），无需手工建库。

#### 2.2.1 工具内置部署（开发环境可用）

```bash
./deploy.sh up mariadb      # 部署内置数据库（按 DB_TYPE 三选一: mariadb / mysql / postgresql）
```

连接信息（地址 / 端口 / 账号 / 密码）自动派生，无需手工配置。

**注意**：内置数据库为单实例 standalone 形态，如需高可用数据库服务，请采用外部独立部署方式；数据库 root 密码仅**首次初始化**生效，已初始化实例改密须同步在库内 `ALTER USER`。

#### 2.2.2 外部独立部署（生产环境推荐）

生产环境下，推荐用户自行搭建高可用的外部数据库服务，搭建完成后需在 `.env.custom` 中填写如下参数，完成外部数据库服务的对接工作：

```bash
# 数据库类型（同时决定连接驱动）
DB_TYPE=mariadb

# 外部数据库服务的连接地址，填写即启用外挂模式
DB_HOST=192.168.1.101

# 外部数据库服务的连接端口，留空按 DB_TYPE 取默认（mariadb / mysql=3306，postgresql=5432）
DB_PORT=3306

# 外部数据库服务的用户名与密码，账号权限区分规则：
# 1. 分库独立账号配置：定义 <模块>_DB_USER / <模块>_DB_PASSWORD（模块集 GATEWAY / WEB / IDENTITY / MANAGER / RUNTIME）
# 2. 全局统一账号配置：仅配置 DB_USER / DB_PASSWORD
# 优先级规则：分库专属账号变量优先级 > 全局统一账号变量；两类同时配置时以分库专属为准
# 说明：AgentServer 连接 Gateway 库，无独立账号变量，凭证跟随 GATEWAY
DB_USER=jswarm
DB_PASSWORD=<统一密码>
```

**密码优先级**：`DB_PASSWORD` > `DB_TYPE` 对应的 ROOT 密码变量，两者均未设置时部署报错（外部数据库必须提供密码）。

#### 2.2.3 多实例数据库隔离

多实例（多命名空间）部署场景下，各模块默认按命名空间自动隔离，无需手动配置：

- **MariaDB / MySQL**：每模块使用形如 `<模块>_<命名空间>` 的独立数据库（如命名空间 `test` 的 Gateway 库为 `gateway_test`）；
- **PostgreSQL**：每模块使用独立数据库 `<模块>`，并以命名空间命名的独立 schema 隔离（如 schema `test`）。

库名 / schema 可用 `GATEWAY_DB_NAME` / `WEB_DB_NAME` / `RUNTIME_DB_NAME` / `IDENTITY_DB_NAME` / `MANAGER_DB_NAME`（PostgreSQL 为 `*_PG_SCHEMA`）显式指定——**请务必保证同一套部署中每个实例的各模块库名（或 schema 名）互不相同**，否则不同实例会读写同一数据库，导致数据串台。

### 2.3 部署对象存储（OBS）服务

系统支持两种对象存储接入方案：部署工具内置部署的 MinIO 实例，或对接外部独立对象存储服务（S3 / MinIO 兼容协议），按需选择。内置 / 外挂的唯一判据为 `OBS_URL` 是否为空。

#### 2.3.1 工具内置部署 MinIO 服务（开发环境可用）

```bash
./deploy.sh up minio        # 部署 MinIO 存储模块
```

连接信息（地址 / 桶名 / AccessKey / SecretKey / HTTPS）自动派生，无需手工配置；内置 MinIO 仅提供集群内访问。

**注意**：内置 MinIO 为单实例 standalone 形态，如需高可用对象存储服务，请采用外部独立部署方式。

#### 2.3.2 使用外部 OBS 服务（生产环境推荐）

生产环境下，推荐用户自行搭建或购买高可用的外部 OBS 服务，搭建完成后需在 `.env.custom` 中填写如下参数，完成外部 OBS 服务的对接工作：

```bash
# 外部对象存储(S3/MinIO兼容)接入地址，填写即启用外挂模式
OBS_URL=obs.cn-north-4.myhuaweicloud.com

# 业务存储桶名称（外部 OBS 必填）
OBS_BUCKET=jswarm-files

# 对象存储访问的 AccessKey / SecretKey（外部 OBS 必填，填写云厂商/兼容 S3 服务的 AK/SK）
OBS_ACCESS_KEY=<AK>
OBS_SECRET_KEY=<SK>

# 客户端连接是否启用 HTTPS
# 生产环境请勿关闭 HTTPS，否则 AK/SK 与业务文件将明文传输；
# 留空默认 false，请以服务端实际 SSL 开关为准
OBS_SECURE=true

# 对象存储区域标识，按需填写
OBS_REGION=

# 对象存储公网预览访问域名
# 仅文件需要浏览器公网直读场景配置，内网环境可不填
OBS_PUBLIC_BASE_URL=
```

**必填校验**：启用外部 OBS 后，`OBS_BUCKET`、`OBS_ACCESS_KEY`、`OBS_SECRET_KEY` 任一缺失部署即报错。

## 3. 产品服务部署与管理

### 3.1 配置 .env.custom

部署工具的全部行为由部署目录下的 `.env.custom` 控制。`.env.custom` 随部署工具安装包一并发布，**大部分变量已预置好，可直接使用**；部署工具包的获取与内容详见 [第 1 节](#1-部署工具包介绍)，基础服务（存储 / 数据库 / OBS）的内置 / 外挂配置见 [2.1](#21-部署存储服务nfs-storageclass)、[2.2](#22-部署数据库服务)、[2.3](#23-部署对象存储obs服务) 节。

部署产品服务前，请务必按集群形态确认以下配置：

```bash
# k8s 集群：请务必设置这个值（默认值是 openshift，openshift 集群不需要专门配置）
CLUSTER_TYPE=k8s
```

### 3.2 部署产品服务

```bash
./deploy.sh up            # 产品组件（按 AGENT_RUNTIME_DEPLOY_MODE 派生）:
                          #   off:     secret → redis → agentserver → gateway → web
                          #   routing: secret → redis → runtime → agentserver → gateway → web
                          #   full:    secret → redis → runtime → gateway → web
                          #          （AgentServer 由 runtime 按需创建，自动注入 Pod 操作 RBAC）
./deploy.sh up manager    # 管理套件: identity → manager-server → manager-web
```



行为说明：

- **namespace**：全部组件由 `NAMESPACE` 统一控制，也可 `./deploy.sh up -n <ns>` 临时指定；数据库建库的库名后缀同样取自 `NAMESPACE`（更换 namespace 即使用对应后缀的独立库）；
- **顺序即依赖**：agentserver 先于 gateway、runtime 先于 agentserver（注册接收方），脚本已保证；共享依赖 secret / redis 缺失时随 `up` 自动拉起，已存在则复用；基础服务（mariadb / minio）缺失时终止并提示，`./deploy.sh up mariadb minio` 拉起即可（已配置外挂数据库 / OBS 时不再要求部署对应内置组件）；
- **幂等**：可重复执行，已存在资源自动跳过；副本数被人为调整过会自动恢复；
- **就绪等待**：每个组件部署后轮询等待 Pod 就绪（默认预算 300s）。首次拉取镜像较慢时调大预算：`WAIT_TIMEOUT_SECS=600 ./deploy.sh up`


#### Manager 默认运行时和容器模板

使用配套版本的 Manager Web、Manager Server 和部署工具，先部署 Runtime，再在同一部署目录、同一命名空间执行 `./deploy.sh up -n <namespace> manager`。工具会将最终渲染的 `conf/agentserver.json` 通过 `jiuwenswarm-manager-runtime-defaults` Secret 只读挂载到 Manager，并设置 `AGENTSERVER_JSON_PATH=/etc/manager/runtime-defaults/agentserver.json`。

OpenShift 部署工具在 Runtime 就绪后，还会将最终配置上传到 OBS/MinIO 的 `defaults/<namespace>/agentserver.json`（可通过 `AGENT_RUNTIME_DEFAULT_CONF_PATH` 调整）。运行时模板列表的“导入默认配置”使用这一对象存储接口，创建配套运行时和容器模板；新建弹窗中的“读取默认模板”和启动自动准备使用上面的只读挂载。两种入口均保留，升级时应同步更新部署工具及 Manager Server，避免只有其中一种配置来源。

Manager 启动后会自动准备运行时模板与容器模板，模板列表中显示“默认”标签。管理员可直接在集群“运行资源”中绑定；需要恢复配置时，在新建运行时模板或新建容器模板弹窗中点击“读取默认模板”，保存后生成独立副本。浏览器无需访问服务器文件系统。重复启动不会重复创建模板；部署配置变化时会生成新的默认快照，保留原有模板和集群绑定。

若只部署 Manager、尚未生成 JSON，Manager 仍可启动，但无法读取默认模板。可先执行 `./deploy.sh up -n <namespace> runtime --render-only`，再重新部署 Manager；只渲染不会启动 Runtime，使用模板前仍需准备实际运行服务和存储。已有 JSON 的目标命名空间必须与本次部署一致，否则应按目标命名空间重新渲染。

升级旧部署包时，更新挂载的仓库源码不会同步独立部署目录。请备份并更新配套部署脚本和模板，保留 `.env.custom`、镜像版本及业务配置，再在实际部署目录执行 `./deploy.sh up -n <namespace> manager-server`。默认模板交付涉及 `deploy.sh`、`template_handler.sh`、`kubectl.sh`、`manager_defaults_handler.sh`，这些文件应与其余公共脚本保持同一版本。JSON、Secret 和生成的 Manager 清单可能含凭据，请按部署配置管理，勿输出完整内容到日志。

### 3.3 卸载产品服务

```bash
./deploy.sh down manager   # 卸载管理套件（倒序: manager-web → manager-server → identity）
./deploy.sh down           # 卸载产品组件（倒序: web → gateway → agentserver → redis → secret）
```

- **数据不可恢复**：PVC / 数据目录随组件一并删除，需要保留请先导出；
- **共享依赖自动保留**：secret / redis 卸载时若仍被存活组件依赖会跳过删除（如先 `down` 产品组时管理套件还在），全部卸载后再补一次 `down` 即可清干净；
- 每个组件删除后脚本会等其 Pod 删净再继续。

### 3.4 只渲染清单（不连集群）

`--render-only` **不连接集群、不做任何部署**，只把 `templates/` 下的清单模板按 `.env.custom` 的配置替换变量，生成可直接使用的 YAML 到 `conf/` 目录：

```bash
./deploy.sh up --render-only -n <命名空间>
./deploy.sh up manager --render-only -n <命名空间>
```

适用场景：生产环境通常不允许部署工具直连集群一键部署，而是用渲染功能生成基准 YAML → 由运维按生产规范修改（镜像仓库、存储类、副本与资源配额、服务暴露方式等）→ 经企业内部评审后，以 `kubectl apply -f`、`oc apply -f` 或 GitOps 等自己的方式部署。

注意事项：

- `conf/` 每次渲染都会整体覆盖，定制后的 YAML 请复制留存（或纳入企业 Git 仓库）；
- 渲染 nfs 组件时，请在 `.env.custom` 中配置 `CURRENT_NODE_NAME`（部署节点名）：离线渲染无法自动识别部署节点，不配置则清单中 nodeName 留空（Pod 可能调度漂移）并输出告警；
- 渲染是纯本地动作，依赖集群实况的处理不会发生（如 k8s 形态的 NFS 数据卷改写、数据库 / 对象存储共享实例地址定位），自行部署前请人工核对；
- 建议保留清单中的资源名称与标签不变，便于版本升级时 diff 工具侧变化。

### 3.5 访问服务

**k8s 形态**：自动追加 manager-web NodePort Service：

```bash
kubectl get svc -n <namespace> jiuwenswarm-manager-web-nodeport
```

访问 `http://<节点IP>:<nodePort>`。

**OpenShift 形态**：部署工具自动为 manager-web 创建 Route，部署完成后查看实际域名（`<name>-<namespace>.<集群ingress域名>`），浏览器从任何网络直接访问，无需 port-forward：

```bash
kubectl get route -n <namespace>
```

```text
https://jiuwenswarm-manager-web-<ns>.<ingress域名>
```

两种形态下，这都是唯一需要记住的入口：从管理面登录后点击进入用户面，**不要直接访问 web 组件地址**（用户面鉴权代理在 manager-web 的 nginx 上）。管理员默认账号 `admin / admin`，首次登录后请立即修改密码。
