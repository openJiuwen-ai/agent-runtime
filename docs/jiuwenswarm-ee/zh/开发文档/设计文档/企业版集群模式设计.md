# 企业版集群模式

本文按 jiuwenswarm `enterprise` 分支上已经落地的行为，描述企业版 Team。第 1 章先说明团队是什么，再说明它在哪里运行、后面每章回答什么。还没落地的能力在第 7 章，代码和数据落点在文末。

## 1. 总览

会话选择到集群模式后，可以创建团队。团队里有一名 Leader，负责拆分任务，并可以拉起若干 Teammate 一起完成任务。`group_id` 和 `bot_id` 都相同的 Web 用户也可以加入，占一个人类座位，和队员一起收发消息。



用户的请求先到 Gateway。Gateway 按这个团队当前所在的会话，把请求送到这台 AgentServer。

```text
用户
  ↓
Gateway
  ↓
这台 AgentServer
  ├─ Leader
  ├─ Teammate
  └─ 人类成员
```



一支团队绑在创建它的那次会话上。后来的请求沿着这个会话，回到正在跑它的那台 AgentServer。Leader 和队员在这台机器的同一个进程里工作。



后面五章按这个顺序写：

| 章               | 这一章回答                 |
| --------------- | --------------------- |
| 建队              | 团队记录从哪里来              |
| 团队配额            | 一个用户能建几个团队，一个团队能有几个成员 |
| 人类成员            | 人类成员怎样加入、发言           |
| 路由到 AgentServer | 后来的请求怎样回到同一台机器        |
| 停止与删除           | 团队停掉或会话删掉之后，名额和路由怎样释放 |

## 2. 建队

这一章覆盖 `team.create` 和聊天里自动建队。团队个数、整队人数和租约见第 3 章。

### 2.1 TeamEntity

表 `team_entity`。所有者是路由三元组，用来推导该 Team 数据所在的工作区。

| 字段 | 含义 |
|---|---|
| `team_id` | 稳定标识，创建时生成。 |
| `team_name` | 展示名，表内唯一。 |
| `owner_user_id` / `owner_group_id` / `owner_bot_id` | 创建者。同范围判断使用 `group_id` + `bot_id`。 |
| `status` | 建队写入 `creating`。`stopped`、`deleted` 见第 6 章。 |
| `runtime_mode` | 当前写入 `local`。 |
| `template_id` | 团队模板。聊天生成的团队可为空或由生成结果填入。 |
| `team_session_id` | 承载该 Team 的会话。 |
| `runtime_team_name` | 会话作用域运行时名，形如 `<team_name>_<session_suffix>`。 |
| `agent_service_id` / `gateway_id` | 字段已保留。创建时为空，Pod 地址记在 `team_route_binding`。 |
| `extra` | JSON。创建时写入 `channel_id`，`team.create` 还会写入 `mode`。 |
| `created_at` / `updated_at` | Unix 时间戳。 |

状态词汇还包括 `running`、`paused`、`stopping`，存储层会校验这些值。当前生产路径只写入 `creating`、`stopped`、`deleted`。

### 2.2 显式创建 `team.create`

一次调用完成模板或描述生成、会话绑定和控制面实体。参数需要 `session_id`，以及 `team_name` + `template_id`，或用于生成名称的 `description`。

```text
校验登录身份和 session 目录
    ↓
reserve_team_create（on_existing=reject）
同时检查模板里预定的非 Leader 人数
    ↓
创建 Team 绑定（模板或生成）
    ↓
写入 TeamEntity，status=creating
runtime_team_name = 会话作用域名
    ↓
更新会话 metadata，bind_session
    ↓
commit_lease，写上 team_id
    ↓
返回 team、binding、session_id
```

用户或组织的团队数已满时不建队，文案见第 3 章。模板里预定的非 Leader 人数超过槽位时也不建队。`team.create` 不解析用户原话。会话上已有未删除实体时返回 `CONFLICT`。绑定或写实体失败时，释放仍为 `reserved` 的租约，并删除刚写下的实体、绑定和团队目录。

### 2.3 聊天里自动建队

聊天的第一次请求先看原话里的整队人数。已经超过上限就拒绝，此时还没有预占名额，文案见第 3 章。通过之后才调用 `reserve_team_create`（`on_existing=skip`）。已有实体的会话直接跳过。预占成功后，流还活着就持有该租约，避免 60 秒到期把名额丢掉。

`team.runtime_ready` 时 `ensure_session_team_occupancy` 把租约提交，并写入 `TeamEntity(status=creating)`。共享库上，预占、插入实体、提交在一次调用里完成。流结束时若租约仍是 `reserved`，则释放。Gateway 断线本身不提交，也不把已提交的团队释放掉。

## 3. 团队配额

这一章覆盖每用户、每组织的团队个数，以及每个团队的整队人数。管理面保存策略并下发到集群网关后，写入 `team_quota_policy`。之后的新建团队和拉起队员按当时命中的策略校验。下调或停用只拦截后续操作，已有团队和已在队成员保持不变。

### 3.1 策略

| 字段 | 含义 |
|---|---|
| `policy_id` / `policy_name` / `policy_desc` | 标识、名称、说明。 |
| `match_expr` | 按 `user_id`、`group_id`、`bot_id` 匹配。空表达式表示全员。 |
| `priority` | 整数，越大越优先。 |
| `max_teams_per_user` | 每用户团队数，1 到 1000，缺省 5。 |
| `max_teammates_per_team` | 整队人数，含 Leader，1 到 1000，缺省 5。 |
| `max_teams_per_org` | 每组织团队数，0 到 1000，缺省 0，0 表示不限制。 |
| `enabled` | 停用后不再命中。 |

没有命中任何已启用策略时，按每用户 5 个团队、每团队 5 人（含 Leader）、组织不限制执行。环境变量 `TEAM_QUOTA_ENABLED` 设为 `0` / `false` / `no` / `off` 时跳过配额。

已启用且匹配当前用户的策略中，`priority` 最大的一条决定该用户的团队数和人数上限。组织上限只采纳表达式里不出现 `user_id`、`bot_id` 的策略，再取其中优先级最高且匹配该 `group_id` 的一条。

占用表是 `team_quota_lease`。计入占用的是 `committed`，以及未过期或被持有的 `reserved`。`released` 不占名额。组织个数按 `group_id` 统计 `team_create` 行，不另写组织租约。`team.stop` 和删除会话对租约的处理见第 6 章。

| 字段 | 含义 |
|---|---|
| `lease_id` | 租约标识。 |
| `kind` | 写入表的是 `team_create` 和 `teammate_spawn`。 |
| `idempotency_key` | 建队为 `session:<session_id>`，队员为 `team:<team_id>:member:<member_name>`。同键重入复用原租约。 |
| `user_id` / `group_id` / `bot_id` | 名额归属的创建者。加入他人团队不另扣团队名额。 |
| `team_id` / `member_name` | 提交后写入。 |
| `status` | `reserved`、`committed`、`released`。 |
| `expires_at` | 建队预占默认 60 秒。聊天流存活期间清空，表示持有。 |

### 3.2 团队个数

`team_quota_account` 是用户建队的互斥行，`team_quota_org_account` 是组织建队的互斥行。建队在同一事务里锁住用户账户行；组织上限大于 0 时再锁组织账户行。检查 `已占用 + 1 <= 上限` 后写入 `reserved`。

```text
reserved（60 秒）
    聊天流仍在 → 清空 expires_at，每 5 分钟刷新
    建队成功 → committed（清空过期时间）
    创建失败且仍为 reserved → released
    持有超过 30 分钟仍未提交 → 后台每 60 秒扫一次并 released
```

超时的 `reserved` 只在确认过期后释放。已经 `committed` 的租约不会被聊天流结束时的释放逻辑清掉。

聊天建队会先解析用户原话里的整队人数。已经超过上限就拒绝，不预占团队名额。`team.create` 不走这道解析。

| 说法 | 理解 |
|---|---|
| N 人团队 / N 个成员 | 整队 N 人，含 Leader。 |
| N 个队员 / N 个专家 | N 名队员，整队为 N+1。 |
| 再加 N 人 / 除我以外 N 人 | 企业版按队员数理解，整队为 N+1。 |
| 范围、至少、至多 | 创建前不拦截，交给队员拉起时的 `spawn_member` 守卫。 |

| 情况 | 结果 |
|---|---|
| 用户团队数已满 | 不建队。文案 `创建失败，一个用户最多有{n}个团队`。错误码 `QUOTA_EXCEEDED`，`kind=team_create`，附带已用、上限、默认值。 |
| 组织团队数已满 | 不建队。文案 `创建失败，一个组织最多有{n}个团队`。错误种类 `org_team_create`，不写入租约表。 |
| 聊天原话要求的整队人数已超过上限 | 不建队，不占团队名额。文案 `无法创建：你要求的是 {人数} 人团队，该团队最多 {n} 人（含 Leader）。` 通知里的 `quota.kind` 为 `requested_team_size`。 |

### 3.3 队员人数

人数上限是命中策略里的 `max_teammates_per_team`，表示整队人数，含 Leader。人数租约只覆盖非 Leader 成员，槽位为 `N - 1`。Leader 座位，以及座位名等于 leader 的 `spawn_member`，直接创建。

`team.runtime_ready` 给 Leader 的 `team_backend.spawn_member` 套上人数守卫，并给 Swarmflow worker 登记同一上限。`team.design` 不走这道守卫。队员租约锁住已有的 `team_entity` 行，同一进程内同一 Team 的 `spawn_member` 再串行一次。

```text
spawn_member
    ↓
Leader 或座位名等于 leader → 直接创建
    ↓
reserve_teammate_spawn
    ↓
同进程执行 Teammate
    ↓
成功 commit；失败或异常 release
```

就绪时按 `team.db` 里除 Leader 以外的名册做一次对账：名册没有的租约释放，名册有而租约没有的补记。补记超限只记日志，不踢掉已经在队的成员。模板预定的非 Leader 人数在 `team.create` 预占时一并检查，超过槽位则不建队，错误种类为 `teammate_spawn`。

| 情况 | 结果 |
|---|---|
| 人数已满 | 拒绝本次加人，队内现有成员不变。文案 `人数已满：该团队最多{n}人（含 Leader），无法再添加队员`。错误码 `TEAM_MEMBER_QUOTA_EXCEEDED`。 |
| 企业版共享库上校验暂时不可用 | 拒绝本次加人。文案 `成员配额校验暂时不可用，本次未创建成员，请稍后重试`。错误码 `TEAM_MEMBER_QUOTA_UNAVAILABLE`。 |
| 队员退出 | 成员关系改为 `left` 时不单独释放人数租约。名册里该座位消失后，下次对账释放。 |

## 4. 人类成员

这一章覆盖 Web 用户以 Human Member 加入、退出、查看和发言。加入和退出是 `team.member.join`、`team.member.leave`。某一个团队的成员名单是 `team.members.list`。当前用户能看到哪些团队是 `team.list`。

### 4.1 TeamMembership

表 `team_membership`。表示哪个登录用户以哪个座位加入哪个 Team。

| 字段 | 含义 |
|---|---|
| `membership_id` | 成员关系标识。 |
| `team_id` | 所属 Team。 |
| `user_id` / `group_id` / `bot_id` | 成员的路由身份。 |
| `member_name` | Team 内座位名。未指定时为 `human-<user_id 的 sha1 前 6 位>`。须匹配 `^[a-z][a-z0-9-]*$`。 |
| `member_type` | 当前写入 `human`。 |
| `display_name` | 展示名。 |
| `permissions` | 默认 `team:view`、`team:send`、`team:task:read`、`team:task:claim`、`team:member:leave`。 |
| `status` | `pending`、`active`、`left`、`revoked`、`expired`。加入路径使用 `pending` / `active`，退出写 `left`。 |
| `expires_at` | 可空。`active` 且已过期时 `is_active` 为假。 |
| `joined_at` / `updated_at` | Unix 时间戳。 |

唯一约束：`(team_id, user_id)`、`(team_id, member_name)`。

### 4.2 加入、退出和查看

调用者是所有者，或与所有者 `group_id`、`bot_id` 相同，才能加入。跨范围加入返回 `FORBIDDEN`，文案为需要邀请令牌。令牌签发尚未实现，见第 7 章。

```text
解析 team_id、session_id 或 team_name
    ↓
所有者，或相同 group_id + bot_id
    ↓
确定座位名，拒绝占用他人座位或非 human 座位
    ↓
运行时已在 → spawn_human_agent → membership=active
运行时未在 → membership=pending
    ↓
team.runtime_ready 时把 pending 座位拉起并改为 active
    ↓
广播 team.membership
```

| 情况 | 结果 |
|---|---|
| 已持有另一个座位又指定新名字 | `CONFLICT`，保持原座位。 |
| 座位被其他用户的 `active` 或 `pending` 关系占用 | `CONFLICT`。 |
| 座位名属于非 human 成员 | `CONFLICT`。 |
| 运行时尚未拉起 | 成员关系保持 `pending`，等 `team.runtime_ready` 再拉座位。 |
| 退出 | 成员关系改为 `left` 并广播。agent-core 里的座位行保留。 |

`team.list` 返回该用户拥有的团队，以及相同 `group_id`、`bot_id` 下成员关系为 `active` 或 `pending` 的团队。`team.get` 要求调用者是所有者或上述成员。`team.members.list` 返回该团队的成员关系、当前用户自己的关系，以及是否所有者。

### 4.3 发言和直播

发消息时用 `resolve_sender_member_name` 取调用者自己的 `active` 座位。客户端带上的别人的 `member_name` 会被丢掉。所有者没有成员关系时按普通 GodView 输入处理。

团队直播每个会话只保留一个等待者，帧发给本进程已连接的 Gateway 推送流。`chat.file` 直接推送，不重复写入历史。

## 5. 路由到 AgentServer

这一章覆盖 Gateway 如何把后续请求送到创建该 Team 的 Pod。

### 5.1 TeamRouteBinding

表 `team_route_binding`。主键是 `team_session_id`，因为第一次 `route()` 时往往还没有 `team_id`。

| 字段 | 含义 |
|---|---|
| `team_session_id` | Leader 所在会话。`shared_user_*` 只是运行时占位，不会写成绑定。 |
| `team_id` | `team.runtime_ready` 回填。 |
| `endpoint` | 该 Pod 的 HTTP 基址。 |
| `agent_service_id` | Pod 标识。 |
| `route_request_id` | 本次 `route()` 的请求标识，用于 touch。 |
| `owner_*` | 首次绑定写入创建者。后续成员命中同一条绑定时不覆盖所有者。 |
| `gateway_id` | 字段保留。 |
| `status` | `creating`、`active`、`unhealthy`、`inactive`。可路由的是 `active` 且 `endpoint` 非空。 |
| `route_version` | `endpoint` 或 `agent_service_id` 变化时递增。只回填 `team_id` 或所有者时不变。 |
| `last_heartbeat_at` | touch 时更新。 |

查找顺序：请求带 `team_id` 时先按 `team_id` 取最近一条绑定，没有再按会话取；没有 `team_id` 时只按会话取。`team.list` 和 `team.quota.get` 不钉绑定，始终走 `route()`。可用 `team_id` 定位的控制方法包括 `team.get`、`team.stop`、`team.member.join`、`team.member.leave`、`team.members.list`。

### 5.2 命中与失败

```text
信封带 team_id，或会话就是该 Team 会话
    ↓
TeamRouteResolver 命中 active 绑定
    ↓
请求发往 binding.endpoint
身份三元组改用所有者，user_id 仍是调用者
    ↓
成功则 touch
    ↓
team.runtime_ready 回填 team_id 和所有者
```

其他成员的 `service_id`、`agent_id`、`workspace_key` 使用绑定上的所有者三元组，因为 Team 数据在所有者工作区。信封里的 `user_id` 仍是调用者，供 AgentServer 校验成员关系。

| 情况 | 结果 |
|---|---|
| 没有绑定，或绑定不是 `active` | 走 agent-runtime `route()`，再 `record_route` 写下 endpoint 和 Pod。 |
| 访问 `endpoint` 失败 | 绑定标为 `unhealthy`，再 `route()` 并刷新绑定。地址或 Pod 变了，`route_version` 才加一。 |
| 后来的成员触发了一次新的 `route()` | 可以更新 endpoint，不覆盖已有所有者。 |
| 删除会话 | 删除对应路由行，见第 6 章。 |

## 6. 停止与删除

停止只允许所有者。删除会话时，调用者不是占用所有者则跳过控制面清理。

| 操作 | 行为 |
|---|---|
| `team.stop` | 停掉该会话上的 Team 运行时，实体改为 `stopped`，该 `team_id` 下的建队租约和队员租约改为 `released` 并保留行。 |
| 删除会话 | 实体先标 `deleted`，再删除实体行和该团队的 `team_membership` 行；按 `team_id` 和建队幂等键物理删除租约；删除 `team_route_binding`。 |
| `team.create` 中途失败 | 释放仍为 `reserved` 的租约，删除刚写下的实体、绑定和团队目录。 |
| 聊天流结束时租约仍是 `reserved` | 释放该次预占。已 `committed` 的团队保持占用。 |
| 进程在持有预占后退出 | 30 分钟无刷新后，后台任务每 60 秒扫一次，释放该 `team_create` 预占。 |

## 7. 尚未实现

以下能力在当前分支没有对应实现。

### 7.1 跨租户加入

- 邀请令牌的签发、过期、撤销和防重放。
- 目标租户、目标用户和权限范围绑定。
- 跨 `group_id` / `bot_id` 的加入。当前直接拒绝。

### 7.2 生命周期和路由增强

- 把 `creating` 推进到 `running`，以及 `paused`、`stopping` 的真实迁移。
- 绑定心跳失联后的自动摘除和恢复。
- 多 Gateway 之间、主库绑定之外的故障切换。当前失败时回退到 agent-runtime `route()`。

### 7.3 分布式 Team

- 按 Team 绑定独立 AgentServer，沿用会话所在 Pod 之外的放置方式。
- 以 `distributed` + `process` + `pyzmq` 作为企业版默认运行方式。Harness 里已有分布式和 A2X 代码，企业版当前写入的 `runtime_mode` 仍是 `local`，`spawn_mode` 默认 `inprocess`。
- Team 运行时恢复、服务迁移。

### 7.4 资源治理和跨 Team 协作

- CPU、内存、Token、LLM 并发配额。
- 扩容申请、审批、临时额度和计费。
- Agent 跨 Team 加入、Team 合并与拆分、任务和上下文迁移。

## 8. 实现落点

控制数据与 Gateway 主库放在一起。`GATEWAY_DB_TYPE` 为 MySQL（含 MariaDB）或 PostgreSQL 时，`TeamStoreActor` 用进程内一条后台线程访问主库。个人版和未登记数据库类型的单测走 SQLite。企业版遇到未登记类型时直接失败，各进程不再各自写一份 SQLite。

`bindings.json`、`.team-meta/team.yaml` 和 agent-core 的 `team.db`（名册、任务、消息）继续使用。用户看到的仍是 `team_name`。企业控制面另记稳定的 `team_id`、所有者和成员关系。运行方式默认 `spawn_mode=inprocess`，控制面把 `runtime_mode` 写成 `local`。

三个仓库的分工：`agent-core` 执行 Leader、Teammate 和人类成员座位；`jiuwenswarm` 承载企业身份、成员、配额和团队路由绑定；`agent-runtime` 负责 AgentServer 拉起、会话亲和和回收。团队个数由 jiuwenswarm 统计。会话亲和是权威路由，`TeamRouteBinding` 是送到当前 Pod 的快速路径，细节见第 5 章。

| 模块 | 路径 |
|---|---|
| 控制面记录、成员、配额 | `jiuwenswarm/enterprise/team/` |
| Gateway 主库表 | `gateway/config/enterprise/tables/team_control_models.py`、`team_quota_models.py` |
| 主库连接 | `gateway/enterprise/db/team_store_actor.py` |
| Team 路由 | `gateway/enterprise/team/route.py`，接入 `RuntimeRoutedAgentClient` |
| 聊天建队、人数守卫、直播 | `jiuwenswarm/server/runtime/agent_adapter/team_helpers.py`、`member_limits.py`、`session_live.py` |
